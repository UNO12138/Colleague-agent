# Linear · 任务状态如何成为团队沟通（阶段草稿）

## 本阶段要回答的问题
本阶段聚焦一个机制：在 Linear 中，任务状态本身是否承担了沟通功能，而不只是进度标记。需要拆解的是：状态如何被定义、谁有权改变状态、状态变化如何被团队感知，以及评论与编辑行为是否与状态变化绑定。

## 初步分析框架
可从四个维度观察 Linear 的状态机制：

1. **状态集合与语义**：状态是否按工作流阶段划分，是否存在“进行中”“待评审”等中间态。具体状态名称与默认配置：待核实。
2. **状态变更的触发者**：由执行者自行推进，还是由评审者或负责人确认。权限规则：待核实。
3. **状态变化的可见性**：变更是否进入团队动态流、是否通知相关成员、是否可订阅。通知粒度与默认行为：待核实。
4. **状态与讨论的耦合**：评论是否挂在任务上、是否随状态流转被要求填写说明、编辑历史是否可追溯。具体交互：待核实。

## 待核实问题
- Linear 的默认工作流状态有哪些，是否支持按团队自定义？
- 状态变更是否会强制或提示填写原因、阻塞说明？
- 评论、状态变更、字段编辑是否在同一时间线中呈现？
- 是否存在“状态即信号”的设计，例如长时间停留某状态触发提醒？

## 设计推论（待验证）
若 Linear 将状态变更与评论、通知整合为同一条时间线，则状态可能从“个人进度标记”转为“团队沟通载体”：成员无需额外发消息，状态流转本身即传递“我完成了什么、卡在哪里、需要谁介入”。这一推论是否成立，需在核实上述交互后确认。
